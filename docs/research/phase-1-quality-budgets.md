# Phase 1 quality budgets

**Status:** Decision for the English-only, one-page Professional Profile at `https://sevipsagis.dev/`.

## Decision

Use WCAG 2.2 Level AA as the normative accessibility baseline. Use Google's Core Web Vitals thresholds and Search guidance as source recommendations, then add small, stricter project guardrails that fit a static page with text and one avatar. A source threshold comes from the cited owner of a standard or metric; a project guardrail is our chosen release constraint and is not presented as an external standard.

## Acceptance matrix

| Area / check class | Acceptance target | Verification | Authority |
| --- | --- | --- | --- |
| SEO — deterministic | The canonical production URL returns `200`, is not blocked by `robots.txt`, has no `noindex`, and is self-canonical. Any public duplicate host redirects to it or is `noindex`. Initial HTML, without running JavaScript, contains the exact approved owner name and professional role in a concise `<title>`, the visible primary heading/intro, and an accurate one-sentence meta description. Profile sections are present as text; email/social destinations use real `<a href>` links with descriptive accessible names. | Inspect the deployed response, headers, `robots.txt`, document source, and rendered document. Fail on a missing/mismatched approved name or role, index block, non-`200` final response, duplicate indexable URL, or script-only profile content. | Google requires crawl access, `200`, and indexable content but does not guarantee indexing; it recommends descriptive, concise titles and useful page-specific descriptions. The name-plus-role placement is a **project guardrail**, not a Google formula. [Technical requirements](https://developers.google.com/search/docs/essentials/technical), [title links](https://developers.google.com/search/docs/appearance/title-link), [snippets](https://developers.google.com/search/docs/appearance/snippet), [crawlable links](https://developers.google.com/search/docs/crawling-indexing/links-crawlable), and [canonicalization](https://developers.google.com/search/docs/crawling-indexing/canonicalization) (accessed 2026-08-08). |

Inspect the request list and image markup. | **Project guardrails** chosen for a text-first static page, not web standards. They are ceilings, not payload targets. Cloudflare Pages already provides CDN caching, validation, and Brotli/Gzip; add aggressive browser caching only for content-hashed immutable assets. | Performance — lab | Median of five cold Lighthouse mobile runs: Performance score **>= 90**, LCP **<= 2.5 s**, CLS **<= 0.1**, and TBT **<= 200 ms**. Missing CrUX data is “not enough data,” not failure, and does not justify adding analytics. | Check PageSpeed Insights/CrUX 28 days after launch and quarterly. Field data wins when it conflicts with lab data; use lab reports to diagnose. | These are Google's current “good” Core Web Vitals recommendations at the 75th percentile, not W3C requirements. CrUX excludes insufficiently popular pages. [Web Vitals thresholds](https://web.dev/articles/defining-core-web-vitals-thresholds), [lab versus field](https://web.dev/articles/lab-and-field-data-differences), and [CrUX methodology](https://developer.chrome.com/docs/crux/methodology) (accessed 2026-08-08). |
| Accessibility — deterministic | The complete page and every responsive state conform to **WCAG 2.2 Level AA**, meaning every applicable Level A and AA success criterion passes. For this page, explicit release checks include: useful avatar alternative text or `alt=""` if redundant; semantic landmarks/headings and reading order; `<html lang="en">`; keyboard-operable named links; visible and unobscured focus; text contrast at least **4.5:1** (**3:1** for large text), non-text contrast **3:1**; text usable at **200%**; no two-dimensional scrolling at **320 CSS px** width except allowed content; and pointer targets at least **24 x 24 CSS px** or a documented exception. Icon-only links target **44 x 44 CSS px** as a mobile project guardrail. | Review the built DOM/accessibility tree and computed colors/sizes. Maintain a criterion checklist with pass, not-applicable, or defect evidence; “not applicable” requires a reason. | WCAG 2.2 AA is **normative for this project**. The 44 px icon-link target is a stricter **project guardrail**; WCAG AA requires 24 px with exceptions. [WCAG 2.2](https://www.w3.org/TR/WCAG22/) (accessed 2026-08-08). |
| Accessibility — lab/manual | Lighthouse Accessibility score is **100** with no failed automated audit, and manual testing passes: keyboard-only traversal/activation, focus visibility/order, 200% text zoom, 320 px reflow, and one screen-reader smoke test of page structure, avatar, and every link. | Test production in current stable Chrome plus VoiceOver/Safari or NVDA/Firefox. Retain the automated report and a short manual checklist before launch and after relevant UI changes. | Lighthouse `100` is a **project guardrail**, not proof of conformance. W3C states that tools cannot check every accessibility aspect and human judgment is required. [WAI evaluation tools](https://www.w3.org/WAI/test-evaluate/tools/selecting/) (accessed 2026-08-08). |
| Accessibility — field | No numeric field metric is required. Any reported blocker to reading the profile or following contact/social links is a release-priority defect. | Keep the published email link as the feedback route; reproduce reports with the user's browser/assistive technology where known. | **Project operating rule.** Analytics would not establish WCAG conformance and is outside Phase 1. |

## Verification cadence

| When | Required checks |
| --- | --- |
| Every relevant change | Deterministic HTML/indexability, transfer budgets, Lighthouse mobile performance/SEO/accessibility, and changed WCAG manual checks. |
| Production launch | Repeat all deterministic and lab checks on `https://sevipsagis.dev/`; save reports and complete Search Console URL Inspection. |
| Post-launch | At day 28 and then quarterly, review Search Console and mobile CrUX if available. Re-run lab/manual checks after content, visual-system, dependency, or hosting changes. |

## Deliberate exclusions

No search-rank SLA, fixed title/meta character count, mandatory structured data, sitemap for this single URL, custom real-user monitoring, analytics beacon, service worker, CMS, or custom performance infrastructure is required for Phase 1. Add one only when observed evidence identifies a problem it solves.

## Remaining inputs and limits

| Item | Effect |
| --- | --- |
| Approved owner-name and professional-role strings are not yet recorded in this decision. | They must be supplied verbatim before the SEO checks can pass. |
| No physical baseline phone model or test geography is specified. | The pinned Lighthouse profile is the reproducible gate; name a physical device only if real-device acceptance is later required. |
| A new personal site may not meet CrUX popularity thresholds or have meaningful query data. | Field rows remain “insufficient data” until data exists; lab and deterministic gates still apply. |
